Shared Principles Across All Three

Regardless of which layout you choose, these principles should govern how content is shown.

1. Three levels of detail everywhere

Glance: A chip or badge showing the key name, scope colour, and win/lose status. Visible without clicking anything.

Scan: The actual value (or heading, or tool name) visible in the row/card. Enough to understand without expanding.

Full: Click to expand and see the complete JSON, full CLAUDE.md text, all MCP tool names, the merge trace, and a plain-English explanation.

2. Scope overlap is always annotated

When two scopes define the same key, both must be visible regardless of which view you're in. This means:

In the Scope Grid (A): both cells are filled — winner is green, loser is struck-through red.

In the Layered Cards (B): scope chips on each key show every scope that touches it, even scopes not currently in focus.

In the Flow Strip (C): source cards sit side-by-side so you physically see the same key in two cards.

3. Merge semantics are visible, not hidden

Every resolved value should show how it was resolved:

selectHighestPrecedence → one scope wins, others are struck through.

appendUnique / setUnion → all contributors are shown with ⊕ icon, resolved shows the combined list.

deepMergeObject → both contribute, but individual keys within the object may win or lose.

This makes the resolution logic learnable by observation.

4. Content types get type-appropriate rendering

settings.json keys: Monospace key-value pairs with type badges (string, bool, string[]). Arrays expand inline.

CLAUDE.md: Heading tree (# → ## → ###) with first-line summaries. Full markdown preview on expand.

MCP servers: Server name + transport + tool count at glance level. Full tool catalog on expand.

Hooks: Event type + handler type at glance. Full command/URL/timeout on expand.

Permissions: Pattern + scope at glance. Evaluation order + wildcard explanation on expand.

5. The context budget is the frame

Every piece of content should show its token cost. This transforms the abstract "200K context window" into something tangible — you can see that your 48-line CLAUDE.md costs 1,200 tokens, and the 12 built-in tools cost 15,500. The budget bar appears in every view as a constant reminder that this is a finite resource being allocated.

Which concept to pick?

A (Scope Grid) is best if the primary question is "for this specific key, what does each scope say?" It's the most information-dense and the most natural for comparing settings side-by-side.

B (Layered Cards) is best if users navigate scope-first ("show me what my project defines") and want cross-references as annotations. It's closest to your existing UI and easiest to build.

C (Flow Strip) is best if the primary question is "how does my config become Claude's behaviour?" — it tells the story from files-on-disk to API request. Best for learning.

My recommendation: use B as the scope-detail view (it enhances what you already have) and C as the pipeline view (it replaces the current "Your Files / The Rules / What Claude Sees" cards with actual content). A could be a "comparison mode" toggle on the resolved-config view.
