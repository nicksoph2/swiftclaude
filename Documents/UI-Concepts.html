A — River Delta: Converging Streams

Multiple configuration streams flow from their sources on the left and converge into a single assembled prompt at the centre. From there the prompt enters the agentic loop on the right — a visible cycle of reasoning, tool use, and verification.

Metaphor: A river system. Tributaries (scopes) feed into a main channel (the assembled prompt), which enters rapids (the agentic loop). You can trace any piece of configuration back upstream to its source.

Design rationale

The current pipeline view presents 8 stages as a flat sequence of boxes. But a Claude exchange isn't really a linear pipeline — it's a convergence of many independent streams that merge into one context, which then enters a cyclical process. This concept makes that convergence visible and tangible.

What it exposes
Every piece of data that enters the prompt — and where it came from. Clicking any source node shows what it contributed. Clicking the convergence shows the assembled context with each segment colour-coded by origin. The loop on the right shows the cyclical nature of tool use.
Interaction model
Click a stream to highlight just that stream's path and what it contributes. Click the convergence to see the full assembled prompt with token counts. Click any loop step to see real tool calls, permission decisions, and hook events from the active session.
What it teaches
That config from different scopes flows together and is resolved by precedence. That the user's message is just one of many inputs. That tool use is a cycle, not a one-shot. That everything is constrained by the 200K context window.
SwiftUI feasibility
Canvas or Path-based drawing for the curves. GeometryReader for node positioning. TimelineView for particle animation. Each node is a standard SwiftUI view with .onTapGesture. The sidebar stays as-is.

B — Layered Anatomy: Cross-Section View

The exchange is presented as horizontal strata — like a geological cross-section. The top layer is the outermost shell (managed/enterprise config), and you drill down through user → project → instructions → tools → the live agentic loop at the core.

Metaphor: An onion or the Earth's layers. Outer layers constrain inner ones. The deeper you go, the more dynamic and session-specific the behaviour. Hover to expand any layer and see its contents.

Design rationale

Your current app already has a "scope stack" in the sidebar, but it reads as a flat list. This concept makes the layering physically visible — outer layers constrain inner ones, and you can see at a glance how deep any piece of config sits. The hover-to-expand interaction lets you focus on one layer at a time without losing the big picture.

What it exposes
The precedence hierarchy as a spatial relationship: outer = more authority. The gradient from static (enterprise) to dynamic (live exchange) is visible as a literal depth axis. Each card shows what that layer contributes to the final prompt.
Interaction model
Hover a layer to expand it and see detailed contents. Click a card to drill into its editor. The "overrides ↑ / overridden by ↓" labels between layers make the merge logic explicit. The depth meter on the right shows where you are on the static↔dynamic spectrum.
What it teaches
That Claude's behaviour is shaped by concentric layers of configuration. That managed settings form an immutable shell. That the live exchange sits inside all these constraints. That overriding works inward — outer layers can block inner ones.
SwiftUI feasibility
Simple VStack of expandable rows with .animation(). Each layer is a standard HStack of cards. The spine colour and gradient background use ScopeColorScheme. Hover detection via .onHover(). Very achievable with current SwiftUI.

C — Timeline Swimlanes: Parallel Tracks

Time flows left to right. Horizontal swimlanes represent the different threads of an exchange: config resolution, prompt assembly, the agentic loop, hooks, and context budget. Cross-lane arrows show how data flows between threads.

Metaphor: A music score or sequence diagram. Each instrument (thread) plays its part on its own staff, but they all synchronise vertically at key moments — the "beats" of the exchange.

Design rationale

This concept foregrounds time and concurrency. Rather than asking "what are the stages?", it asks "what happens when, and how do the threads interact?". It's particularly powerful for understanding the agentic loop — you can see each think→tool→result cycle as discrete events, with hooks and permissions firing at precise moments between them.

What it exposes
The temporal flow: what happens first, what happens in parallel, what blocks what. The hooks firing before and after each tool call. The permission gates. The context budget growing as tool results come back. Great for understanding the agentic loop as a real process.
Interaction model
Horizontal scroll for long sessions. Click any event to see its payload. Toggle swimlanes on/off in the sidebar to focus on specific threads. "Replay" mode plays through a recorded session step-by-step. "Live" mode updates in real-time during an active session.
What it teaches
The temporal ordering and dependencies. That hooks bracket every tool call. That permissions are checked per-call. That context grows over time and may trigger compaction. That a single user prompt can cause dozens of tool calls in a loop.
SwiftUI feasibility
ScrollView(.horizontal) with VStack of lane rows. Events are coloured capsules. Phase headers are a sticky top bar. The budget lane uses a ProgressView or custom shape. Session replay requires transcript parsing (already built).

D — Circuit Board: Wired Components (Bonus)

Config sources, resolvers, and runtime components are shown as labelled chips on a circuit board, connected by colour-coded traces. Data flows along the traces like current. You can tap any chip to inspect its inputs and outputs.

Metaphor: A printed circuit board. Each configuration source and processing stage is a chip. Traces (wires) show data flow. Power rails represent the scope hierarchy. Signal direction shows information flow.

Design rationale

This concept is the most literal representation of the data flow architecture. It treats each config source and processing stage as a discrete component, connected by visible "traces" that carry data. The grid background and junction dots reinforce the circuit metaphor. It's particularly good for understanding the resolver stage — where multiple inputs merge into resolved outputs.

What it exposes
The exact data flow graph: which sources feed which resolvers, how resolvers feed the prompt builder. The bus rails show scope authority. Animated pulses show data movement. Clicking any chip shows its inputs and outputs.
Interaction model
Click a chip to inspect its data. Hover a trace to highlight the full path from source to API. Toggle scope traces in the sidebar to isolate one scope's path. Zoom into resolver chips to see the merge waterfall. The grid snaps components to a clean layout.
What it teaches
That the system is a directed graph of transformations. That multiple sources converge at resolver nodes. That the prompt builder is the final aggregation point. That the API call is the output of the entire circuit.
SwiftUI feasibility
Canvas for the grid and traces. ZStack with positioned views for chips. Matches your existing DiagramLayout and DiagramEdgeFlow infrastructure closely. Animated dots via TimelineView. Most directly maps to your current pipeline architecture.

My take

These aren't mutually exclusive. The strongest approach would be to combine elements: use B (Layered Anatomy) as the default "overview" since it's the most immediately readable, then let users switch into A (River Delta) for the convergence view or C (Timeline Swimlanes) when exploring a live/recorded session. D (Circuit Board) maps most naturally onto your existing 8-stage pipeline and DiagramLayout infrastructure, so it could replace the current pipeline view with minimal architectural change.

The common thread across all four: your current UI shows configuration as static data panels. All four of these concepts instead show configuration as something that flows — from source to resolution to prompt to execution. That sense of movement is what will make the exchange logic legible.
